# 后端开发规范：本项目补充约定

确认日期：2026-10-12。

本约定配合项目根目录的《后端开发规范.md》使用。原文件为只读，保持原样；其中关于 `modules` 的职责与依赖方向按以下已确认约定补充。其他要求继续遵循原规范。

## 1. 框架与环境

- 后端采用 Flask、SQLAlchemy、Pydantic；替换早期开发计划中的 FastAPI 选择。
- 沿用 `project311` 环境，当前已核实 Python 3.11.16，符合原规范要求。
- 首版本机实现继续使用 SQLite、本地文件存储和持久化本地通知队列。
- 依赖按 `requirements/` 分环境锁定；配置统一通过 `backend/config/` 读取，维护 `env.example`。ORM 模型变更通过迁移脚本实施。

## 2. 目录职责

| 目录 | 职责 | 本项目示例 |
|---|---|---|
| `backend/utils/` | 无业务判断的基础工具 | 日期转换、字符串处理、哈希计算 |
| `backend/common/` | 通用组件 | 统一异常、日志、安全组件 |
| `backend/data/` | SQLAlchemy 模型与持久化操作 | 任务、结果、租约、通知记录 |
| `backend/schema/` | Pydantic 输入输出契约及字段映射 | 任务提交、查询、结果结构 |
| `backend/service/` | 核心业务规则与业务操作编排 | 创建任务、执行准入、租约校验、投递、重试、结果提交 |
| `backend/controller/` | HTTP 路由及请求响应衔接 | 接收上传、任务查询、取消入口 |
| `backend/modules/` | 后台程序运行入口与流程组织 | 启动 Worker、投递器，管理运行循环与停止信号 |

采用原规范要求的三级目录，例如 `backend/modules/worker/asr_worker.py`、`backend/modules/dispatcher/task_dispatcher.py`、`backend/service/task/task_service.py`。这些路径是建议布局，不代表代码已经存在。

## 3. 依赖方向

```text
backend/modules → backend/service → {backend/data, backend/common} → backend/utils
backend/controller → backend/service → {backend/data, backend/common} → backend/utils
```

- `modules` 和 `controller` 复用同一套 Service；Service 不反向依赖这两类入口。
- `modules` 负责程序启动、停止与循环组织；任务是否能执行、租约是否有效、是否重试等判断由 Service 实现。
- `modules` 不绕过 Service 直接修改任务、租约或结果，也不复制一套业务规则。
- `data` 不依赖 `service`，`utils` 不依赖项目其他层，禁止循环依赖。
- 测试可以按测试目标调用对应层；测试代码不得成为生产代码依赖。
- 模块间采用绝对导入；工具复用遵循原规范的 Utils First 原则。

## 4. 与平台架构的关系

- M01—M15 表示架构中的逻辑职责，不要求每个编号都对应一个 `modules` 子目录或独立进程。
- M08 的首次投递与失败重试规则位于 Service，投递器入口位于 `modules`。
- M12 的模型调用编排、容量检查和结果提交位于 Service，Worker 运行循环位于 `modules`。
- M05、M06、M07 即使首版共享本机基础设施，也继续区分任务档案、文件和通知三类职责。

## 5. 开发顺序与当前状态

先实现 Data、Schema、Service，再通过 Controller 接入 HTTP，通过 Modules 接入后台运行循环。所有外部输入按原规范通过 Pydantic 校验。
