## 5. 真实启动、停止、重启与边界

通过交付的 PowerShell 脚本，已实际验证：

| 场景 | 实测结果 |
|---|---|
| 启动 | 四服务与真实模型就绪；5000 健康、运行状态、5173 页面及代理响应正常 |
| 重复启动 | 返回已有实例，实例编号与四个服务 PID 不变 |
| 正常停止 | Worker、投递器、API、前端依次收到停止；管理器确认 Job 内进程清空 |
| 独立退出确认 | 验收脚本在停止前打开管理器、四服务及模型 child 的原进程句柄，停止后全部收到退出信号，避免仅凭 PID 判断 |
| 无关进程 | 验收脚本另外创建的独立 Python 测试进程在平台停止后继续存活，最后由测试自己的 Popen 句柄清理 |
| 重复停止 | 正常返回，没有删除数据库、模型或音频 |
| 端口被占用 | 临时占位监听器占用 5000 时启动返回 2，没有创建四服务；原监听器仍可连接 |
| 全部重启 | 再启动获得新实例；通过 HTTP 读取本次真实任务，与停机前结果完全相同 |
| 最终停止 | 管理器未运行，状态 stopped；5000/5173/4173 均不可连接，API/页面探测均为 false |
| 原数据 | 原 8 条任务状态及结果指纹全部不变；新增本次成功任务后共 9 条：7 成功、2 取消，无非终态任务 |

最终一轮 API/投递器/Worker 的退出码均为 0；前端 Python 包装进程记录为 `4294967295`，其内部 Node 通过 Windows 控制信号结束，因此不声称所有进程都以 0 退出。是否真正停止以 Job 清空、原进程句柄退出和端口释放共同确认。

报告：[script-lifecycle.json](../../runtime/verification/part7/script-lifecycle.json)，各脚本 stdout/stderr 保存在同目录 `start-*.log`、`stop-*.log`、`status-*.log`。首次端口冲突验收的测试监听器只留一个连接等待位，被状态命令探测占满；修正测试监听队列后完整复跑通过，未修改业务代码来绕过验证。

最后只读检查：[final-checks.json](../../runtime/verification/part7/final-checks.json)。已核对后台/前端报告计数、92个唯一函数编号、交付文档本地链接、SQLite quick_check=ok及9条终态任务；[最终进程检查](../../runtime/verification/part7/final-process-check.json)没有发现本项目相关运行进程或上述端口监听。

独立代码审查发现并修复了：状态写入异常阻断停止清理、启动等待锁阻塞停止请求、首次状态落盘前中断漏发停止，以及重复启动时探测失败仍称就绪。对应测试通过，并由独立复核确认修复到位。

## 6. 复现命令与交付边界

日常运行按 [README](../../README.md) 的检查、启动、状态和停止命令。完整环境准备、配套备份、迁移、模型校验、四窗口排障及日志定位见[使用指南](../使用与故障处理.md)。浏览器复跑使用唯一证据目录，避免覆盖本次交付记录。

管理器是本机生命周期工具，任何一个服务进程退出时会记录故障并停止同实例其余服务；不自动重启故障服务，也不配置开机自启。进程没有退出但内部故障时，仍需看页面运行报告和日志。启动阶段校验模型就绪，不等于持续监控设备资源。

首版仍不包括账号认证、Node Agent、多节点调度、GPU、Redis/对象存储、YOLO、LLM、集中指标告警、生产部署和规模容量。固定在途 20、单 Worker 是开发规则，不是通过压测的容量承诺。真实长音频、多语言、噪声与准确率评测没有完成。原 v2.1 文档、规范和架构展示网页没有修改或发布。
