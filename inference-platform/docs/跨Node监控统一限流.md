# 跨 Node 监控统一限流

> v2.26增量：查询许可、墓碑和Node恢复状态可随成套离线快照原样保存，隔离恢复不会清空名额或自动重查；见[备份恢复](本地成套备份与隔离恢复.md)。

本轮只做监控查询的公共名额控制。多个 Node 查询业务状态或取回结果前，先向同一个中心平台申请许可：全平台最多4个，同一个业务服务最多1个。查询结束后归还。推理执行、任务排队、业务内部队列和模型内存管理不属于这些名额。

这是本地开发与隔离验证交付；真实多主机网络、Linux、Redis和模型继续待验。日常库未迁移，日常进程未重启，没有接入校园网。

## 实际数据流

```text
Node 本地保存本次查询编号
    → 中心 SQLite 事务核对原调用并预约查询名额
    → Node 保存已获准状态
    → 查询业务状态，必要时串行获取结果
    → 保存可信快照/结果
    → Node 保存待归还记录
    → 中心幂等归还名额
```

状态和结果请求在同一份名额内串行执行。Node 仍有进程内4个/同地址路径1个的保护，但它不能代替中心许可。自动采集和显式核对都使用中心许可；浏览器GET只读保存的快照，不申请名额、不查询业务。

中心读取已持久化的调用身份，核对调用编号、次数、两端修订、Node、服务、启动实例和派发事实。Node不能通过请求自行指定服务分组或额度。中心使用`BEGIN IMMEDIATE`同时检查全局与服务占用；没有持有数据库写锁进行HTTP通信。

## 同一服务的识别

默认按中心不可变目标配置里的业务地址和状态路径识别。相同远端地址/状态路径共用一个名额；`localhost`和回环IP属于所在Node的本机命名空间，不把两台服务器的`127.0.0.1:8003`当成一台服务。

同一业务服务若通过多个域名、代理地址或路径接入，管理员须在中心目标的`monitoring.budgetGroup`填写相同编号，例如：

```json
{
  "monitoring": {
    "protocol": "job-json-v1",
    "statusPath": "/status/{requestId}",
    "resultPath": "/result/{requestId}",
    "budgetGroup": "lab-asr-instance-01"
  }
}
```

服务管理页面的监控配置中已有“查询共享组（可选）”。它与GPU共享资源组、应用并发额度是不同资料，不增加推理容量。共享组只能在保存新修订时改变；已有调用保留原修订。存在查询占位时，应先排空原查询，再更改同一物理服务的分组或地址别名，避免管理员把同一服务拆成不同身份。平台不通过DNS猜测别名关系。

相同业务地址/状态路径还有独立保护，即使误填不同查询共享组，仍只能同时查询一次。同一调用也不能通过更换查询编号重叠查询。没有新增字段的旧目录修订保持原内容和指纹。

## 配置与启用条件

中心显式提供独立私密环境变量：

```text
INFERENCE_COMMON_EXECUTION_ENABLED=true
INFERENCE_MONITOR_TOKEN=<独立生成的32—256位非空白ASCII随机值>
```

目标Node在自己的私密环境文件配置：

```text
NODE_MONITOR_CENTRAL_URL=http://central-server:5000
NODE_MONITOR_TOKEN=<与该中心INFERENCE_MONITOR_TOKEN相同>
```

查询凭据不能复用应用Key、入口、Node管理/执行/上报或业务凭据。不把真实值写入目录JSON、日志、示例或Git。该凭据只给受信Node控制面使用；持有它的Node属于同一可信控制域，不作为不可信租户的独立权限边界。远程部署时需在后续真实部署阶段配置内网访问限制及TLS；本轮没有验证跨主机连通。

中心新增显式Alembic迁移`20261022_0021`，增加`monitoring_permits`账本，不改旧任务、结果和推理许可。Node继续使用独立`0004`库，在既有逐调用JSON中保存恢复状态，不共享中心SQLite文件。

仅配置查询凭据时，中心启动会要求0021；不自动迁移。旧0020未配置查询凭据仍兼容原公共API。新建6A隔离环境会初始化0021并生成第六份独立查询凭据，旧验证目录不会覆盖或自动升级。日常0014本轮保持，未来正式切换须按原计划备份、核对在途任务并显式迁移，再正常重启匹配版本的中心与Node。

启用前先停旧采集器并确认其在途查询已经结束，再启用所有目标Node的新版采集器与中心预算。旧版Node不申请许可，不能与新版本混跑并声称全局上限成立。平台推理任务仍按原规则核对和保留，停止采集不表示可以清理推理占位。

## 断连与重启规则

| 情况 | 行为 |
|---|---|
| 全局4个或同服务1个已满 | 记录等待原因，默认5秒后再试；不向业务发查询 |
| 中心未配置或不可用 | 暂停新状态/结果查询，按5/10/20/40/60秒退避；保留上次可信进度，不改推理终态 |
| 申请可能已成功，应答丢失 | Node保留申请编号；下一次先幂等归还，再申请新编号，不直接执行查询 |
| 归还比迟到申请先到达 | 中心留下已归还墓碑；迟到申请不能激活原编号 |
| 查询结束，归还应答丢失 | 保存待归还记录并退避重试；重复归还不会影响其他查询 |
| 已保存可信业务结果，归还暂失败 | 推理结果仍正常保存/结算，查询名额保留待归还；终态调用也继续处理归还记录 |
| Node查询途中退出 | 重启后原查询标为未确认，中心占位不因心跳、时间或重启自动清除 |
| 中心进程重启 | 从SQLite原账本继续；不重置成4个空位 |

不存在TTL自动归还。中心账本和Node恢复资料都需纳入后续备份；首版不自动清理许可/墓碑历史。查询名额不足可能导致进度显示延迟，不允许通过删账本、改Key或改服务别名绕过。

正常查询返回、超时或协议错误后，客户端本次HTTP操作已经结束，执行归还；该归还只表示平台停止本次查询，不证明推理已经停止。原业务查询404/429/格式错误的规则继续保留。

## 明确核对未确认查询

管理员须先确认旧Node进程、本次查询客户端以及相应业务查询已停止，再在目标Node调用：

```text
POST /node/v1/admin/executions/{invocationId}/monitor-budget/release
Authorization: Bearer <Node管理凭据>
Content-Type: application/json

{"queriesStoppedConfirmed": true}
```

必须是真正JSON布尔值`true`。观察凭据、中心执行凭据及应用Key均不能调用；本机仍有该查询/操作在运行时拒绝。中心不可用时保留待归还，不伪报成功。该操作不查询/取消业务，不更改推理状态或释放推理并发额度。

这是一项带事实确认的管理操作，不能仅因为任务已超时或页面无进度就提交。若Node恢复库丢失，应先恢复对应资料并核对中心账本，不直接删中心占位。

## 页面、事件与接口文档

任务详情新增“查询名额”：展示等待全局/服务名额、中心许可不可用、归还待确认、原查询未确认。原服务进度、监控异常、推理结果状态继续分别显示。

Node记录查询预算原因变化；相同等待原因不重复追加，正常每次申请/归还不刷满事件时间线。中心采集到等待原因变化时，记录来源为平台的`invocation.monitor_budget_wait`，不冒充业务上报。

内部接口只有独立凭据可调用：

- `POST /internal/v1/monitor-budget/acquire`
- `POST /internal/v1/monitor-budget/release`
- `GET /internal/v1/monitor-budget/openapi.json`

申请和归还提交`pollId`与原`ExecutionCommand`，回应`held/released/denied`及受控原因。新接口不加入入口Node公共白名单，所有响应`no-store`，不返回原业务响应或秘密。

保存的协议见[monitor-budget.openapi.json](monitor-budget.openapi.json)、[Node OpenAPI](node-foundation.openapi.json)。验证结果另见[本轮记录](阶段记录/跨Node监控统一限流-验收记录.md)。本轮交付讲解后暂停，真实部署及用户验收仍待完成。
