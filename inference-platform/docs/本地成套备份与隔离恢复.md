# 本地成套备份与隔离恢复

这一部分先解决“能把一套平台资料保存下来、能在新目录恢复核对、恢复副本不会重复执行任务”。**当前只支持6A建立的单中心＋单Node独立验证环境，不操作日常0014数据库，也不提供正式切换或解除隔离命令。** 多主机、真实Redis、Linux以及日常历史迁移继续在后续部分验收。

## 保存哪些资料

| 内容 | 保存方式 |
|---|---|
| 中心任务、结果、事件、配置修订、应用权限和Key摘要 | 完整SQLite快照，当前0021 |
| 中心并发占位、查询许可、租约、broker身份和outbox | 原样保留，不清空、不重置期限、不重新投递 |
| Node服务、实例、控制操作、执行去重和未知调用 | 独立Node SQLite快照，当前0004 |
| 上传音频/图片 | 保存`uploads/`受管文件，并核对每个任务引用的大小与SHA256 |
| 运行日志及验收问题快照 | 保存`logs/center/`、`logs/node/`普通文件，不复制锁文件 |
| ASR手工接口配置侧文件 | 存在时保存`db/center.sqlite3.asr-services.json` |
| 这套环境的启动配置和私密凭据 | 保存为私密JSON证据，不生成可启动的恢复env |

模型、Docker镜像、业务服务内部数据、Redis的AOF/RDB、源码、依赖、临时文件和操作系统不在本次备份范围。推理结果目前主要在SQLite中；下载时生成的TXT/JSON无需单独造一份历史结果文件。CPU/GPU内存、显存管理仍由业务侧负责。

首版要求中心派发记录全部属于这套Node，Node调用身份必须与中心记录一致。涉及其他Node或缺少配套资料时拒绝发布，不把单机快照称为完整集群备份。

## 备份前提

源目录必须是6A工具创建并有`deployment-validation.json`、`READY`和成套私密配置的独立验证环境。两端路径、凭据和中心地址须匹配，数据库版本须是0021/0004。不会为了备份自动升级旧库。

先正常停止该验证环境的中心API、执行器、Node及其他控制写入进程，再明确提供`--controllers-stopped-confirmed`。这表示确认控制面和采集器已停止，**不表示未知业务推理已停止**；未知推理及其占位照常保留。

工具还会尝试取得已知进程锁、上传/接口配置锁，以及两库的SQLite写入屏障。锁被占用就退出，不杀进程、不删锁。写入屏障覆盖两库快照与文件采集；SQLite backup API纳入已提交的WAL数据，不直接复制正在变化的数据库主文件。文件和配置前后重新核对，出现变化、上传暂存未完成、引用文件缺失或损坏都会拒绝发布。

这些检查不能代替操作者核对所有非合作写入进程；停止确认不是自动扫描整台主机的承诺。

## 操作示例

在项目的`inference-platform/`目录使用已有Python3.11环境。下面只新建独立演示资料，不读取日常.env：

```powershell
$recoveryProject = (Resolve-Path '.').Path
$recoverySource = Join-Path $recoveryProject 'runtime/deployment-validation/recovery-demo'
$recoverySnapshot = Join-Path $recoveryProject 'runtime/deployment-validation/recovery-demo-snapshot'
$recoveryTarget = Join-Path $recoveryProject 'runtime/deployment-validation/recovery-demo-restored'

python -m backend.modules.deployment.linux_cli init --root "$recoverySource" --name recovery-demo
python -m backend.modules.deployment.recovery_cli backup --root "$recoverySource" --output "$recoverySnapshot" --controllers-stopped-confirmed
python -m backend.modules.deployment.recovery_cli verify --snapshot "$recoverySnapshot"
python -m backend.modules.deployment.recovery_cli restore --snapshot "$recoverySnapshot" --output "$recoveryTarget"
```

上述演示源未启动进程，才可确认已停止。已有验证环境需要先正常关闭其进程，不能直接照抄确认标志。所有路径必须是绝对路径，输出父目录已存在，最终输出目录必须全新；项目工作区内仅允许忽略的`runtime/deployment-validation/`。源目录、其父目录和子目录不能作为输出，不覆盖旧备份或旧恢复目录。

命令返回0表示该操作成功，2表示检查失败。输出只含快照编号、文件数、版本/数量及隔离状态，不打印Key、配置正文、聊天、转写或原异常响应。`verify`读取已保存文件，不访问Redis、SSH或业务服务。

`.pending-*`为工具预留目录名，不能作为正式输出目录。

## 完整性和发布

快照有文件清单`manifest.json`及其摘要标记`COMPLETE`。校验包括：

- 清单结构、文件白名单、重复/越界路径、大小和SHA256。
- 文件集合完整，不允许额外未登记文件或缺少必要的两库/配置/隔离标记。
- SQLite完整性、外键、版本、中心/Node调用身份及任务上传引用。
- 普通文件和目录要求，拒绝符号链接、Windows重解析点、硬链接及特殊文件，包括SQLite旁的WAL/SHM/journal路径。

首版上限为单文件64MiB、总文件内容256MiB、清单4MiB、清单文件9998个。超限拒绝，不截断、不静默丢文件。达到这些规模后须在后续扩大工具容量并重新验证，不能把本版当作不限规模的生产备份工具。

先在同一父目录的私密`.pending-snapshot-*`或`.pending-restore-*`目录完成写入和核对，最后以不覆盖目标的原子目录重命名发布。不支持安全发布的平台会拒绝。失败时保留待检查资料，不自动递归删除或续做；`.pending-*`不能通过正式快照校验。若在最终发布之后遇到存储错误，命令仍可能报错，应显式核对目标目录，不能盲目覆盖重试。

SHA256用于发现损坏和不一致，不是签名或加密。快照含原始上传、结果和私密配置，须保存在可信私有目录，不上传Git、不贴到聊天中；POSIX创建目录0700、文件0600，Windows沿用所在目录的ACL。Linux权限、掉电持久性、异地存储和加密备份没有在本轮验收。

## 恢复后为什么不能直接运行

备份中的数据库和恢复数据库旁均有`*.restore-quarantine.json`。恢复根目录另有`RESTORE_QUARANTINED.json`，启动资料只放在`recovery/config/*.private.json`，不生成`READY`或运行env。中心/Node数据库入口、应用工厂及中心执行器遇到隔离标记会在开始运行前拒绝。

尚未发布的`.pending-snapshot-*`、`.pending-restore-*`路径即使还没写完数据库旁的标记，也禁止启动；恢复根标记仍在时，误删单个数据库旁标记也不会放开运行。畸形标记同样按隔离处理，不把读不懂当成允许启动。

恢复操作不会：

- 启动中心、Node、容器、模型或后台采集器。
- 把未知调用改成失败/成功，释放推理或查询名额。
- 更换调用身份、配置修订、任务编号、broker身份或重新派发通知。
- 自动迁移版本、恢复Redis消息或重放LLM响应。

已确认结果、排队记录、应用Key摘要及撤销记录、未知占位、未归还查询许可都保持备份时的原值。租约虽然可能已过期，也不会因此在恢复期间调用恢复器释放容量。

本轮不提供解除隔离命令。不能通过删除标记就把恢复副本当成可上线环境；它仍可能落后于旧平台的最新状态。后续正式切换须确认旧平台唯一退出、核对备份点之后的任务/结果和Key撤销、逐项核对未知调用与查询占位、检查Node实例和服务配置、安排Redis通知恢复及凭据策略，再单独授权上线。原业务仍在运行时，只取回同一调用的可信结果，不能重做推理。

隔离标记用于防止工具误启动，不是防范同一操作系统账户刻意改文件的安全边界。只读核对仍可使用`verify`以及受控的SQLite只读工具；本轮没有开放恢复副本的管理页面或外部接口。

启动守卫需要本轮及后续版本的代码。旧版本程序不识别这些标记，不能拿旧程序打开备份或恢复数据库；后续切换也必须统一组件版本。
