## 1. 已决定的自动选择与目标执行方式

平台采用**受控计算目标编号 `target_id`**，由后台登记把编号绑定到已有服务的地址、协议、模型兼容信息和已核实的设备。普通用户仍选择模型并提交任务，默认由平台决定哪个目标获得执行资格；维护操作如需指定目标，只接受已登记编号，不接受用户提供任意URL、Python代码或系统命令。

2026-10-19用户进一步明确：平台侧的规则、数据结构、接口、资源观测方案及性能参数测定均由开发侧自行完成，不让服务方决定每个任务使用哪张卡，也不要求服务方先建设监控接口。已有文档、可访问源码和获准的只读部署信息优先自行核查；仅对无法核实的真实部署事实、资源可使用范围、共享限制和访问/测试权限提问。参数由获准范围内的实际测量确定，不把设计选择当作真实容量。新增采集器或上游服务改造仍需相应权限；模型部署启停职责保持不变。当前最小询问见[ASR服务对接清单](ASR服务对接清单.md)。

- 首选：一个已有服务入口固定对应一种已核实的设备。设备由服务方部署配置固定；平台调用对应入口，不启动或切换远端模型进程。
- 若现有服务经实际协议验证支持请求级设备选择，再在受控适配器内映射参数。不能把文档中含义未知的 `device_id` 直接填成 `cuda:0` 或 `cpu`。
- `cuda:0` 只是某个服务进程可见的设备序号，不能跨机器、容器直接比较。设备记录区分节点、稳定物理设备标识和服务内设备定位符；未核实的字段保留未知。
- 当前 `https://10.8.21.33:8003` 继续作为设备未知的同步调用通道。给它起目标编号不会证明它使用GPU；本轮不登记或改库，现配置和结果不变。

例如，未来的 `asr-gpu-a`、`asr-gpu-b`、`asr-cpu-a` 可以分别指向已核实的目标；这些只是命名示例，当前没有这三个真实目标。

## 3. 目标选择与CPU承接规则

选择发生在执行前。ASR仍进入原能力队列，绑定目标的调用Worker主动领取；`service/asr`中的统一“外部调用目标准入策略”决定该目标此刻能否领取候选任务。

1. 先筛选模型/输入兼容、绑定配置有效、观测新鲜、健康、对应调用Worker可工作且目标/共享组均有许可的候选。目标容量与共享组容量都计入`held`和`uncertain`请求。
2. 对合格GPU目标，按“已占用许可/配置限额”从小到大选择，稳定`target_id`打平。这是可解释的容量规则，不宣称按显存或GPU利用率取得全局最优。
3. CPU仅处理尚未执行的任务。首轮只有该任务候选池中的GPU容量已确认不足或明确没有配置可用GPU目标时，且CPU目标有新鲜容量、模型兼容、实测支持预计排队与处理耗时满足剩余截止时间及CPU预算，才允许CPU承接。
4. 相关GPU状态未知/过期不能当作“满载”。没有CPU性能样本时自动CPU承接保持关闭，不随意设定30秒/60秒等“小任务”阈值。音频时长可复用现有实测字段，阈值与耗时估计在真实CPU验证后确定。
5. 无合格目标时保持原期限排队或由原超时规则收尾。任务已执行或结果不明时，不复制到CPU或另一个GPU重跑。

设备未知的现通道保留旧同步调用资格，与GPU优先候选池区分；它的成功、繁忙或断线都不构成GPU/CPU选择证据。

## 4. 领取、占位与未知结果

- 领取通知前按同一策略预筛；取得原执行租约的同一写事务内再次核对目标、共享组容量和任务资格，原子占用许可。服务层裁决，data层持久化，modules只组织运行。
- 当前通知领取与执行租约是两个事务。候选目标失去资格时，必须按通知owner/token安全归还可见，不误确认消息、不增加attempt、不刷新任务原截止时间；避免不合适的CPU或落选GPU长期隐藏队头任务。具体事务衔接在2A实现时验证。
- 断网、超时、本机调用进程退出或心跳过期均不证明远端执行结束。`held/uncertain`继续占目标及共享组许可；仅确认终态或沿现有人工核对规则释放。
- 对多个执行槽，停止/恢复/退出核对须逐项处理活动调用，不能只取第一条。未知请求保留原目标修订和共享组，不通过换编号、换模型版本或重启Worker绕开。
- 同一通知/任务重复领取仍受原leaseToken、dispatchVersion、executionPlanVersion和幂等规则保护，不增加第二套权威任务状态机。
- 现有本机Whisper与外部SenseVoice不是同一模型的CPU/GPU两个副本，不能自动互相替换。旧模型规范不可覆盖；容量策略独立于模型版本，迁移中无法反推的历史目标信息保持未知。
