# 实验室ASR资源核查说明

适用阶段：v2.12本机-3A。本文是可复用的只读核查步骤，**保存说明不表示命令已经执行、资源已经核实或真实路由已经启用**。本轮非交互SSH认证未成功，后经用户明确授权的Edge/1Panel终端取得主机3块GPU/48逻辑CPU、8003监听，以及实际SenseVoice CPU配置与该监听PID所指日志的启动后CPU Provider记录；日志无PID，不等于逐请求CPU执行已证实。可调用GPU目标/设备对应、获准共享容量和CPU任务范围性能仍待核实，路由保持禁用；完整时点/证据见[3A阶段记录](阶段记录/本机-3A-实验室真实目标与资源接入-验收记录.md)。连接别名本身不是硬件证明；上传、SSH密钥配置、Linux部署及模型启停仍按原约定暂停。

以下为可复用的分步说明；本轮第一步和部分第二步已有实际证据，后续重点是GPU调用目标/设备绑定、共享容量及CPU真实调用性能，不因保存命令就记完成。初次采集先取得第一步的三份短输出即可，不需要一次提供全部资料。命令应在你已经获准登录的实验室Linux终端执行，不能在笔记本PowerShell中执行。不使用sudo，不安装工具，不重启服务，不修改配置，不扫描网络。命令不存在、权限不足或没有输出时，保留原提示即可。

## 第一步：取得硬件和8003端口快照

### 1. GPU型号、稳定标识和当前显存/利用率

```bash
nvidia-smi --query-gpu=index,name,uuid,memory.total,memory.used,memory.free,utilization.gpu --format=csv
```

UUID用于以后区分具体GPU；编号可能随部署或重启变化。空闲显存、低利用率只是这个时点的观测，不能直接解释成允许平台使用，也不能直接换算为可接收的ASR并发数。

### 2. CPU、内存和负载概要

```bash
LC_ALL=C top -b -n 1 | head -n 5
```

只保留前五行的系统概要，不输出整个进程列表。单次CPU百分比和负载不是性能测试，也不能证明已有可调用的CPU模型实例。

### 3. 固定8003端口的监听进程

```bash
ss -ltnp 'sport = :8003'
```

这是查询本机一个已知端口，不连接ASR、不发送音频。记下实际监听地址及PID；若看不到PID，先写“权限不足，PID待核实”，不要自行提升权限。若是容器代理等转发进程，只能证明端口由它监听，还不能认定它执行模型。

回复时注明服务器、实际执行时间，附这三份输出即可。第一步只能回答“有哪些硬件、当时负载怎样、8003由哪个可见进程监听”，不能证明服务绑定了哪块GPU、同模型CPU服务可用或共享并发上限。

## 第二步：按已确认的PID核对进程与部署资料

取得第一步结果后再做。本节示例的`12345`必须换成第一步实际确认、属于获准ASR服务的PID；如果还没有明确PID，先停在第一步。每个确认过的ASR执行进程分别核对，不遍历其他项目的进程或配置。

### 1. 读取该进程的基本身份

```bash
ps -p 12345 -o pid,ppid,user,comm,lstart
```

只显示PID、父PID、用户、程序名和启动时间，不打印完整启动参数或环境变量。启动时间用于识别PID是否被后来的无关进程复用；如果与前一次记录不一致，重新核对，不沿用旧绑定。

### 2. 读取该进程的工作目录

```bash
readlink -f /proc/12345/cwd
```

目录只是定位已有部署资料的线索，不证明实际加载了该目录内的配置。权限不足就记待核实，不读取`/proc/12345/environ`，也不输出`cmdline`。

### 3. 对照当前GPU计算进程

```bash
nvidia-smi --query-compute-apps=pid,gpu_uuid,used_gpu_memory --format=csv
```

只保留与已经确认的ASR进程对应的行，不需要转发其他项目的行。8003的API进程可能把推理交给独立Worker或容器，因此没有同PID行不等于ASR一定在CPU上运行；有同PID行也只证明当前关联，不证明所有请求固定使用它。若出现独立Worker，先凭现有部署资料确认其身份，再单独核对，不根据进程名字猜测。

然后在获准查看的已有配置中，只核对下列字段含义并记下结论及来源文件路径，不粘贴整份配置、`.env`、密码、令牌、私钥或完整启动命令：

| 核查项 | 要确定的事实 |
|---|---|
| 服务入口 | `config/server_config.yaml`中实际监听地址/端口如何对应8003及当前进程；若有代理或容器，谁转发到哪个已确认服务 |
| 模型与协议 | `config/model_config.yaml`中的`asr.default_engine`、实际使用的SenseVoice模型位置和输入输出能力；版本号未知可以继续记录未知 |
| 设备绑定 | `worker.devices`及实际加载的ONNX执行Provider如何生效，CPU/GPU绑定是否适用于同步`/transcripts`；源码支持不等于本次部署启用 |
| 目标区分 | 是不同固定服务入口，还是有已经核实的请求参数可以指定设备；只有一个自动分配入口时，不虚构为多个固定目标 |
| 共享限制 | GPU、CPU和服务是否供其他项目使用；已有允许使用范围、并发限制和占用报告来自哪里，是否覆盖所有调用方 |

文档中的`device_id`目前只有“可选”说明，不猜测其类型、`cpu`或`cuda:0`等取值。部署侧`worker.devices`也不自动成为请求参数。若实际配置与文档不同，记录差异，先核对真实部署。

## 从只读事实到真实接入

先形成“入口—进程—设备—模型”的证据对应，再决定登记哪些禁用目标。已有固定入口优先复用；同一服务的别名仍共享容量，不能因为多写一个地址而增加许可。GPU利用率/显存和CPU负载，与服务可接受并发数分别记录；没有共享容量依据时，平台保持原限额1、设备unknown，不按快照猜测并发。

如已有获准的资源接口，先读其真实契约；没有接口时，由开发侧设计最小只读采集方式，需要新增部署或修改服务时再取得相应权限。报告须保留来源、采样时间和有效期，区分目标与共享组；未知或过期不能视作空闲，也不能当作GPU已满。

CPU承接另需真实的同模型CPU调用目标，以及允许的小规模测量范围。目标和调用方法尚未确定前不发送音频。确定后先在允许时段、并发1下使用既有公开短中文音频核对结果与耗时，再按实际允许范围补充不同长度样本；不能用一份短音频外推全部300秒任务，也不把本机Whisper当作外部SenseVoice的等价CPU副本。

测量记录应关联目标修订、音频时长、完整请求耗时、测量时间、实际并发及运行条件；后续据实确定有效期、适用音频范围、固定开销、每秒音频耗时、安全余量、排队上界和可接受预算。模型版本不是必填项，但同模型/能力兼容仍需要现有配置或实际调用依据。没有CPU证据时，可先核实GPU目标，CPU承接保持关闭。

只读快照、资料登记、真实性核实、真实调用和用户验收分别记录。本说明不会解除现有隔离门禁，不启用真实新增目标，不修改旧任务、容量许可或未知结果；结果不明的请求不会换设备重发。
