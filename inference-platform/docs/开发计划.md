**进入条件：**前三阶段交付，用户单独授权，并取得[ASR服务对接清单](ASR服务对接清单.md)中实际可提供的资料。只有真实服务必须使用GPU而当前无可用条件时等待；这不阻塞前三阶段的本机CPU开发。

- 有可用调用接口时先实现真实适配器，核对完整音频/流式输入、参数、同步/异步完成方式、通用结果和引擎专属信息；不猜测字段，不伪造分段时间戳。
- 若仅提供已经运行的服务接口，将其标为外部调用服务，不显示或声称可以启停。只有同时获得部署包/镜像/源码、管理命令或API以及实际权限，才接入启停管理并验证。
- 模型名、版本、运行环境、资源需求和失败/取消语义均以真实资料和实测为准；凭据使用本地安全配置，不写入文档或普通聊天。
- 本路线不要求新增第二个额外模型，不重新接入YOLO/LLM，也不以此阶段自动开展多节点调度。

**验收：**真实音频通过对方服务取得并转换实际结果，验证错误、超时和取消边界；能管理的服务另验启动、模型就绪与停止确认，不能管理的服务明确记录“仅调用”。旧任务、版本与结果保留，交付后暂停，后续13—16另行确认优先级。

## 第三部分：实现上传、任务创建与查询

**目标：让平台能够记住“谁提交了什么任务、现在是什么状态”。**

对应M01、M02、M03、M04、M05、M06的首批能力。

开发内容：

1. 建立固定模型配置和Pydantic数据契约。
2. 通过Alembic建立任务、幂等记录、待投递事件等数据表。
3. 将音频分块保存到受管目录，通过内部文件引用访问，不接受用户指定服务器文件路径。
4. 在同一事务中保存任务、幂等记录和待投递事件。
5. 实现以下接口：

| 接口 | 用途 |
|---|---|
| `GET /api/models` | 查询支持的模型 |
| `POST /api/tasks/asr` | 上传音频并创建任务 |
| `GET /api/tasks` | 分页查询任务列表 |
| `GET /api/tasks/{task_id}` | 查询单个任务 |

接口JSON字段采用`camelCase`，Python内部使用`snake_case`，由Schema统一转换。执行计划版本在后台统一命名为`execution_plan_version`。

**验收：**

- 提交成功后得到任务编号，重启后台后仍可查询。
- 相同幂等键和相同内容返回原任务；不同内容返回冲突。
- 文件保存或数据库写入失败时，不产生虚假的成功受理。
- 文件上传未形成任务时，有明确的临时文件清理规则。
- 此阶段任务显示`created`，明确提示尚未接入执行流程。

**本部分成果：**上传与任务管理接口、数据库迁移、接口测试。

**需要理解：**音频文件、任务档案和待发送通知为什么分开保存。

## 第四部分：打通队列与Worker自动执行

**目标：提交任务后，由后台自动完成真实转写。**

实现主链路：

**M02创建任务 → M05保存 → M08首次投递 → M07通知队列 → M12主动领取 → M05保存结果。**

开发内容：

1. 建立M07的持久化通知表与发布、领取、确认接口。
2. 实现M08首次投递和失败补投；任务表与通知表共用SQLite，但保持独立职责。
3. 建立独立的API、投递器、Worker运行入口，均复用Service。
4. Worker一次只执行一个任务，模型加载完成后才接单。
5. 完成租约申请、续期、结果提交与过期提交拒绝。
6. 模型推理放在独立子进程，续租与控制检查不被转写阻塞。
7. 增加结果接口`GET /api/tasks/{task_id}/result`和运行状态接口`GET /api/runtime`。
8. 执行失败能够保存错误；本阶段尚不自动重试或接管。

**必须同时保证：**

- 本地投递通过事务协调通知写入、投递记录和排队状态，不将`running`回退为`queued`。
- 重复通知不能重复启动同一次有效执行。
- 结果持久化成功后才确认消息。
- 租约失效不等于推理进程停止；确认执行结束后才释放槽位。
- Worker状态来自实际报告，不能伪装成完整GPU资源监控。

**验收：**

- 接口提交真实音频后，可以查询到最终文字。
- 多个任务依次执行，模型运行期间API仍可响应。
- 重复通知、续租、过期提交和结果重复提交测试通过。

**本部分成果：**不依赖操作页面也能运行的真实ASR异步后台。

**需要理解：**M08为什么必须参与首次投递；领取消息为什么还需要申请租约。

## 第六部分：补齐取消、有限重试和故障恢复

**目标：让异常有明确处理，不让任务一直停留在“处理中”。**

开发内容：

1. 区分不可重试的输入错误和允许重试的暂时故障。
2. 扩展M08，处理执行租约到期、等待超时和有限重试。
3. 增加`POST /api/tasks/{task_id}/cancel`，并启用页面取消操作。
4. 未执行任务直接取消；执行中先标记`cancel_requested`，请求停止受管推理子进程。
5. 确认子进程结束后释放槽位；无法确认停止时保持不可接单并报告异常。
6. 用事务条件更新裁决取消与成功提交的竞争，保护已确定终态。
7. 区分排队期限、单次执行期限、任务总期限和租约期限。

采用以下可配置的本机开发初值：

| 参数 | 初值 |
|---|---|
| 执行并发／最大在途任务 | 1个／20个 |
| 文件大小／音频时长上限 | 20MiB／5分钟 |
| 排队期限 | 首次受理后10分钟 |
| 单次执行／任务总期限 | 15分钟／30分钟 |
| 最大执行尝试次数 | 2次，包含首次 |
| 租约有效期／续期间隔 | 30秒／10秒 |
| 重试等待 | 5秒 |

上述数值用于开发验证，不表示已验证容量。等待资源不消耗执行失败次数，重投不刷新首次受理时确定的等待与总期限。

**验收：**

- Worker退出后任务可按规则恢复，旧租约结果不能覆盖新结果。
- 等待超时、重试耗尽和不可恢复错误最终进入明确失败状态。
- 排队取消、运行取消及取消与提交竞争得到一致结果。
- 结果已保存但消息未确认时，不重复推理。
- 通过故障注入和可控时钟验证异常，避免人工等待完整超时时间。

**本部分成果：**具备首版异常处理能力的ASR后台和操作页面。

**需要理解：**心跳、租约、任务终态和资源释放分别说明什么。

- 页面展示真实节点/实例及数据新鲜度；区分未发现GPU、探测失败、数据过期/未知，未知资源不能当作可用资源。过期节点或实例不得用于新的放置/接纳判断。
- 登记、心跳和状态规则放service，持久化放data，采集/Agent入口放modules。现有Windows管理器与未来Agent的控制边界在本阶段记录清楚，暂不增加另一套自动拉起逻辑。

**验收：**真实CPU、内存、进程与模型实例可核对；实际启停/重启引起正确状态变化。测试重复登记、旧会话/迟到心跳、过期和探测失败；模拟GPU仅用于隔离测试，不显示成日常真实能力。旧ASR/图片流程保持可用，交付后暂停。

**需要理解：**一台节点与一个模型实例为何不同；有心跳为何不等于模型一定可接单。

### 14B：多节点与GPU实测登记

**目标：**把14A登记与状态规则扩展到真实远程节点，获得可核对的GPU及实例信息。

**进入条件：**14A与13C交付，具有实际多节点连接及可用GPU，用户要求实施。当前为**已规划、未开始，等待外部条件**。

- 接入实际节点通信、节点身份和凭据，采集真实GPU设备、显存/占用、进程、实例及心跳，区分硬件探测与模型实际运行状态。
- 验证网络中断、节点重连、Agent重启、重复登记和旧会话拒绝；过期状态不能持续被选为可放置或可接纳资源。
- 页面区分各真实节点及资源来源；没有访问或探测权限时明确未知，不用模拟上报代替实测。

**验收：**多台真实节点及GPU信息可与服务器实际情况核对，至少在实际支持的GPU上验证现有模型实例就绪，并验证断联/恢复和过期隔离。不同模型引擎的GPU支持逐项记录，不由一个模型成功推断全部支持。交付后暂停。

## 第十五部分：资源调度与受控恢复

**本部分分为15A、15B、15C，当前均已规划、未开始。M10决定模型实例放在哪里、需要几个；ASR/YOLO仍由Worker主动领取M07各自能力队列中的任务，不改为M10逐条派发任务。**

### 15A：单节点放置计划与资源预留

**目标：**根据真实本机资源和模型需求生成可核对的实例放置计划，先保证判断与预留一致，再由15B执行计划。

**进入条件：**14A交付，用户要求实施15A；先测量现有模型加载、运行时资源使用及资源波动，为系统和已有进程保留余量。

- 定义人工指定期望副本数的入口和校验，依据新鲜节点/实例状态、实测模型需求和安全余量决定是否可放置，持久化计划及拒绝原因。CPU使用率不是可直接分割预留的容量，计算和内存预算需说明测量依据。
- 实现原子资源预留、竞争冲突和幂等处理，核对计划、预留和已报告实际占用的关系，防止同一实例重复扣减或真实占用被遗漏；过期/未知状态采取保守判断。
- 默认只为现有ASR和Vision各一个CPU实例制定计划；额外副本须在资源预算、实例身份和锁约束验证后才允许，不用笔记本试验宣称集群容量。
- 本阶段只产出计划与预留，不自动启动/停止模型进程。尚未执行且没有实际占用的预留可按规则撤销；已执行或停止未确认的实例不得因预留超时就当作资源已释放。

**验收：**真实资源输入下可解释地接受或拒绝计划；验证并发预留、幂等重放、资源不足、过期状态、占用核对和重启后计划保持。测试虚拟资源用于规则覆盖，真实资源测量单独记录。确认没有自动启停进程，交付后暂停。

**需要理解：**实例放置与任务领取为何分开；预留资源为何不能与实际占用重复计算。

### 15B：本机实例执行与受控恢复

**目标：**把15A的计划落实为可追踪的本机模型实例启动、停止和有限恢复，使实际进程与计划能够对账。

**进入条件：**15A交付，用户要求实施15B。执行前必须明确现有Windows管理器与M11 Agent中谁拥有每个实例的启动、停止与恢复权，禁止两者同时监控并自动拉起同一实例。

- 按实例ID/会话执行幂等指令，处理已有同类型固定Worker身份、文件锁和状态报告，避免重启/重试覆盖另一实例。仅控制本项目确实受管的进程，不能凭过期PID操作无关进程。
- 启动后先等待模型就绪，再允许接单；停止先退出新任务接纳/领取，按规则等待在途任务完成或受控停止。ASR/YOLO仍使用能力队列和既有租约，LLM服务不因本阶段自动获得本机进程管理能力。
- 确认受管推理进程结束后再释放槽位与相应预留；停止、启动结果或退出情况不明时标记异常/不确定并阻止新分配，不能只改数据库状态就宣称释放。
- 由M10依据当前部署计划、资源快照和恢复策略授权恢复，同一实例只保留一个有效恢复决定；M11/本机执行器仅执行仍有效的决定，不自行绕过计划拉起模型。对进程退出、启动失败、命令重放、管理器重启设置有限恢复次数、退避与总时间边界；保留操作结果和失败原因，避免无限重启及重复创建。模型实例恢复与单个任务重试分别计数和裁决。

**验收：**使用已有真实CPU模型执行启动、就绪、停止、重启与有限恢复，核对进程和计划/资源一致；覆盖在途任务、迟到命令、旧会话及重复执行，确认没有双重管理或提前释放。额外同类副本只有在本阶段条件具备且实测通过才单独登记支持。交付后暂停。

**需要理解：**停止接单为何不等于进程已结束；恢复模型实例与重试一个任务有什么区别。

### 15C：多节点与GPU调度验证

**目标：**将本机验证过的计划、预留、执行与恢复机制用于真实多节点和GPU，验证跨节点资源决策。

**进入条件：**13C、14B、15A、15B交付，已有实测模型资源需求与可用节点/GPU，用户要求实施。当前为**已规划、未开始，等待外部条件**。

- 依据准确模型能力、实际GPU/显存、节点状态和安全余量进行跨节点放置与原子预留；仍以模型实例为调度对象，不将每条ASR/YOLO任务硬绑定某个Worker。
- 验证实例创建、就绪、摘除/排空、受控停止及容量调整；策略阈值依据实测制定，保护在途任务，不能直接套用设计中的示例容量。
- 验证并发计划、网络分区、节点失联/重连、重复命令、启动失败和恢复限制；区分逻辑过期与物理GPU进程仍运行，防止显存超配、重复实例及过早释放。

**验收：**真实跨节点/GPU放置和至少一次容量调整有完整证据；故障时既有任务租约/结果规则保持一致，资源占用与账本可核对。硬件不足以覆盖的场景保持待验证，交付后暂停。

## 第十六部分：指标、容量与整体验收

### 16A：本机指标与性能基线

**进入条件：**15B交付，用户要求实施16A。仍使用现有CPU模型，不为达到目标数字盲目放大文件限制或增加副本。

**验收：**指标能与实际任务/进程记录核对，至少完成一次真实本机小规模基线并可复跑；记录性能波动、瓶颈和未覆盖项，不外推服务器/GPU或2000在途能力。交付后暂停。

**需要理解：**请求数量、正在推理数量和实例数量为何不同；模型准确率与推理速度为何需分别评估。
