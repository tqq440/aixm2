# 旧版本迁移隔离演练

这一步解决“旧版数据库升到新版后，原有资料会不会被改掉”。工具自己生成一份0014版测试库，复制后升级到0021，再逐表核对。**本轮只用合成资料，没有备份、复制、迁移或切换日常数据库。**

## 演练内容

| 测试资料 | 检查内容 |
|---|---|
| 8个ASR/视觉任务、8份合成上传 | 编号、状态、结果、输入引用、原始字节和哈希保持 |
| 成功、排队、运行、失败、取消任务 | 迁移不改变执行次数、期限、租约、幂等记录和旧通知 |
| ASR已释放、占用中、结果未知许可 | 1个held、1个uncertain原样保留，不重发、不释放 |
| 2个LLM请求 | 已完成记录及1个uncertain在线占位保持，不保存聊天正文 |
| 模型和版本、接口侧文件 | 版本信息、调用配置指纹、结果指纹保持 |
| 目标/共享组、目录/路由、过期资源观测 | 选择记录、未知设备、旧观测不因升级变成可用资源 |
| 0014已有的全部表 | 逐表列名、结构及索引摘要、全部行内容摘要保持 |

旧迁移0005自带的Whisper模型目录也保留；另外加入3个合成模型，不下载或加载模型文件。夹具只允许在无业务记录、仅含该基线目录的0014库里写入；已存在业务资料或版本不符时拒绝。CLI本身也不接受外部源库路径。

旧表共26张，不计版本表，计入SQLite内部的`sqlite_sequence`；加上`alembic_version`共27张。对比原表使用有类型的行内容摘要，不依赖查询返回顺序。版本表单独核对0014→0021；升级新增17张表。

新公共调用、应用、Key、任务事件、Node派发、查询许可和outbox均为空。只有0017迁移规定的Redis安装身份记录被建立，状态为`unknown`。**没有因为升级而连接Redis，也没有将旧任务自动转入公共执行链路。**

工具还会重复执行升级，确认表内容和安装身份保持；测试另用Alembic结构检查确认升级后与当前ORM一致。已有旧占位仍能被公共容量守卫识别；正式切换前必须逐个核对，不能清空来“腾容量”。

上传内容是专用合成字节，不是可以用来验收ASR/YOLO准确率的真实音频、图片；工具不解码、不加载模型、不启动任何Worker。

## 命令

在`inference-platform/`下使用项目已有Python环境：

```powershell
$migrationProject = (Resolve-Path '.').Path
$migrationDemo = Join-Path $migrationProject 'runtime/deployment-validation/legacy-migration-demo'
python -m backend.modules.deployment.migration_cli run --output "$migrationDemo"
python -m backend.modules.deployment.migration_cli verify --root "$migrationDemo"
```

`run`只接受一个全新的绝对路径；父目录必须存在。项目工作区内只允许忽略的`runtime/deployment-validation/`，不覆盖已有目录或输出到源码目录。没有`--source`、日常数据库、运行环境、启用或解除隔离选项；不读取日常`.env`及父进程的`INFERENCE_*`设置。

`verify`只读已发布的演练资料，不再次升级。返回0表示一致，2表示检查失败；输出仅含版本、数量、演练编号和隔离状态，不打印结果正文、配置正文或原始异常。

## 输出与隔离

```text
新目录/
  legacy/db/center.sqlite3              # 合成0014原库
  legacy/uploads/                      # 合成输入
  upgraded/db/center.sqlite3            # 原库快照升级到0021
  upgraded/uploads/                    # 同一批合成输入
  RESTORE_QUARANTINED.json              # 根隔离标记
  migration-evidence.json               # 文件/旧表证据
  COMPLETE                             # 证据摘要
```

两份数据库旁另有`*.restore-quarantine.json`，接口侧文件也分别保留。所有文件有大小和SHA256证据；白名单、完整文件集合、数据库完整性/外键/版本、原表保持性、新表状态和隔离标记均参与校验。缺文件、额外env、越界/重复路径、链接、坏摘要、历史变化或意外新调用记录均拒绝。

先在私密`.pending-restore-legacy-*`目录完成演练和核对，再以不覆盖目标的原子重命名发布。失败保留暂存资料，不删除或自动续做；未发布目录不能通过正式`verify`，也不能启动数据库。

源库和升级库都沿用恢复模块的启动隔离守卫，中心应用及数据库入口会在启动前拒绝；没有`READY`或运行env。数据库迁移本身通过明确指定路径的Alembic连接进行，不走应用启动和恢复执行入口。只能使用识别隔离标记的当前代码查看，不能拿旧版平台启动这些测试库。此机制防止误操作，不防范同一系统账户蓄意改库或删守卫。

证据上限沿用单文件64MiB、总内容256MiB、清单4MiB；这里只允许固定23个演练文件、每表最多10000行，不能当作不限规模的生产迁移工具。POSIX新目录0700、新建文件0600，Windows沿用父目录ACL；真实Linux权限和掉电恢复仍待验。

## 与正式迁移的区别

这次证明当前迁移脚本能保留所覆盖的0014合成历史，不代表日常42个任务已迁移，更不代表整个平台已切换到新架构。正式迁移仍需独立安排：

1. 暂停新受理，唯一旧执行链路和旧采集器正常退出；核对在途、未知调用及共享额度。
2. 为真实旧库、上传、接口配置和日志建立匹配版本的备份方案，并处理备份点后的新增结果/任务及Key撤销。上一部分0021＋Node0004备份工具不能直接用于0014日常库。
3. 升级真实副本，核对原资料与新配置、应用归属及各Node实例；旧任务不能凭空补造详细日志或绑定新调用。
4. 完成独立Redis/Lua/重启、Linux、多Node网络和真实服务协议验收，再安排唯一执行链路启用、结果回传与通知恢复。

校园网暂不可用的原环境问题继续保留在验收日志中。本轮不重试SSH，不部署或启停服务方容器，不管理模型内存/显存，不安装依赖或下载模型。实际开发验证见[验收记录](阶段记录/旧版本迁移隔离演练-验收记录.md)。
